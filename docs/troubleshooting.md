# 트러블슈팅 · 문제 해결 사례

개발·배포 중 겪은 버그와 구조적 문제를 **증상 → 원인 규명 → 해결과 선택 근거 → 배운 점** 순서로 정리했습니다. 사례마다 담당자와 커밋을 남겨 `git show <hash>`로 근거를 확인할 수 있습니다.

> **분석의 근거**: 커밋 diff, 코드, Spring·JPA의 동작 방식에 근거한 설명입니다. 당시 로그나 지표를 따로 남겨 두지는 않았기 때문에, 커밋 메시지에 원인이 적혀 있지 않은 부분은 `[분석]`으로 표시한 **사후 판단**입니다. 원인을 잘못 짚었던 경우도 숨기지 않고 회고로 남겼습니다.

## 1. 다른 사용자의 좋아요·검색 기록을 조작할 수 있던 구조 — IDOR

**담당** 곽동욱 · **커밋** `c7130c0`(CustomUserDetails) → `bf8099e`, `eb659e2`, `4f76d60` · **일시** 2025-11-20

**증상**
초기 API는 사용자를 요청 파라미터로 받았습니다.

```http
POST /api/v1/likes/artists/5?userId=3
GET  /api/v1/search/history?userId=3
DELETE /api/v1/search/history/10?userId=3
```

JWT 필터는 이미 있었지만 **인증만 확인하고 "누구인지"는 파라미터를 믿었습니다.** 로그인한 사용자가 `userId`만 바꾸면 다른 사람의 좋아요를 추가·삭제하고 검색 기록을 볼 수 있는 구조였습니다(OWASP의 Broken Access Control / IDOR). 검색 기록 삭제의 "본인 기록인지 확인" 로직도 비교 대상인 `userId`가 요청값이라 의미가 없었습니다.

**원인**
당시 필터는 토큰 `sub`(이메일) 문자열만 principal로 넣었고(`Collections.emptyList()` 권한), 컨트롤러가 꺼내 쓸 **사용자 객체가 SecurityContext에 없었습니다**. 개발 초기 Swagger에서 테스트하기 쉬운 파라미터 방식을 그대로 둔 것입니다.

**해결**
1. `CustomUserDetails`(`UserDetails` + `OAuth2User`)를 만들고, 필터가 토큰 `sub`로 `User`를 조회해 principal로 저장(`c7130c0`, `de50ec7`).
2. 좋아요·검색·검색 기록·추천 컨트롤러 전부에서 `@RequestParam Long userId`를 제거하고 `@AuthenticationPrincipal CustomUserDetails`로 교체(`bf8099e`, `eb659e2`, `4f76d60`).
3. 서비스의 소유권 검사(`history.getUser().getUserId().equals(userId)` → `403 FORBIDDEN_ACCESS`)가 이제 **서명 검증된 값**과 비교하므로 실제 방어가 됩니다.

**배운 점**
- **인증(누구인가 확인)과 식별(누구로 처리할지)은 같은 출처여야 합니다.** 클라이언트가 보낸 식별값은 그것이 ID든 이메일이든 조작 가능한 입력입니다.
- 이후 새 API는 모두 principal에서 사용자를 꺼내는 것을 기본 규칙으로 삼았습니다([ADR 7](design-decisions.md#7-사용자-식별값은-요청이-아니라-토큰에서-꺼낸다)).

## 2. 좋아요 개수 경계값이 계속 어긋난 문제 — "작업 전 상태" vs "작업 후 상태"

**담당** 곽동욱 · **기간** 2025-11-10 ~ 12-03 · **커밋** `85feba0` → `816e083` → `7b87e55` → `68375a3`·`74bd079` → `6e65ef8`·`d51c25c`·`ddc640e`·`17b0ca8`

가장 오래 끌었고, 가장 많이 배운 문제입니다.

**규칙**: 좋아요(아티스트+공연 합산)는 최소 2개, 최대 N개(5 → 10 → 50).

### 경과

| 날짜 | 커밋 | 변경 | 결과 |
| --- | --- | --- | --- |
| 11-10 | `85feba0` | `checkMax`: `total >= 5`(추가 전 호출) / `checkMin`: `total <= 2`(삭제 전 호출) | 단건 추가·삭제에서는 **정확** |
| 11-25 | `816e083` | 최대 5 → 10 (`>= 10`) | 정확 |
| 11-25 | `0161458` | 온보딩 `selectArtists` 추가: 아티스트를 모두 저장한 **뒤에** `checkMax`, `checkMin` 호출 | 같은 함수를 **"작업 후"** 에 호출하기 시작 |
| 11-25 | `7b87e55` | "10개까지는 가능하도록" `>= 10` → `> 10` | 온보딩에서 10개 선택은 통과. 그러나 **단건 추가(작업 전 호출)에서는 10개 상태에서 11번째가 허용됨** |
| 11-28 | `f680e5c` | 아티스트 다건 삭제 도입, `checkMin`은 여전히 현재 개수만 봄 | 4개에서 3개를 한 번에 지우면 1개가 남아도 통과 |
| 11-29 | `74bd079` | "일반 유저여도 게스트로 뜨는 오류" — `userRepository.save(user)` 추가 | (아래 분석 참고) |
| 11-29 | `68375a3` | `checkMin`: `<= 2` → `< 2` | 온보딩에서 2개 선택이 통과. 그러나 **단건 삭제(작업 전 호출)에서 2개 상태에서 삭제가 허용 → 1개가 남음** |
| 12-03 | `6e65ef8` 외 3건 | `checkMin(userId, countToDelete)`로 **작업 후 개수** 기준 통일, `checkMax`는 추가 전 `>= 50`만, 온보딩의 후행 `checkMax` 제거 | 모든 호출부가 같은 의미 |

### 원인

```
삭제 전에 호출:   현재 2개 → "지우면 1개가 되니 거부"  → 조건: current <= 2   (= after < 2)
온보딩 후에 호출: 현재 2개 → "2개면 충족이니 허용"    → 조건: current <  2
```

같은 숫자 2를 두고 **호출 시점에 따라 올바른 부등호가 달랐습니다.** 하나의 함수가 두 의미로 쓰이는 한, 한쪽 증상을 고치면 다른 쪽이 깨질 수밖에 없는 구조였습니다. 최대 개수(`>= 10` vs `> 10`)도 똑같은 이유로 엎치락뒤치락했습니다.

### "온보딩을 마쳐도 GUEST로 남는" 버그의 실제 원인 `[분석]`

`74bd079`는 role 승격 뒤에 `save(user)`를 추가했지만, `selectArtists`는 `@Transactional`이고 `user`는 같은 트랜잭션에서 `findById`로 읽은 **영속 상태**라 변경 감지(dirty checking)로 커밋 시 UPDATE가 나갑니다. `save()` 없이도 반영되는 코드였습니다.

같은 날 들어간 `68375a3`이 실제 원인을 해결한 것으로 보입니다. 당시 `checkMin`은 `<= 2`였으므로 **최소 개수인 2개를 고르면 예외 → 트랜잭션 전체 롤백 → 좋아요도 role 승격도 취소 → GUEST 유지**가 됩니다. 프론트는 `isFirstLogin = true`를 받고 다시 온보딩 화면을 띄웁니다. 2개를 고르는 사용자가 많은 최소 경계값이라 자주 재현됐을 것입니다.

> 회고: 증상("GUEST로 보인다")에서 "저장이 안 됐다"를 떠올려 `save()`를 추가했지만, 실제로는 **저장이 롤백**된 것이었습니다. 응답 상태 코드(400 `LIKE_MIN_REQUIRED`)를 먼저 확인했다면 바로 찾을 수 있었습니다.

### 해결

```java
// 작업이 끝난 "뒤"의 개수로 판정. 호출부가 몇 개를 지울지 명시한다.
public void checkMinLikes(Long userId, int countToDelete) {
    if (getTotalLikes(userId) - countToDelete < 2) throw new CustomException(LIKE_MIN_REQUIRED);
}
```

| 호출부 | 인자 | 의미 |
| --- | --- | --- |
| 온보딩(저장 완료 후) | `0` | 이미 반영된 현재가 곧 결과 |
| 공연 단건 취소 | `1` | 하나 지운 뒤 |
| 아티스트 다건 취소 | `distinct().size()` | n개 지운 뒤 |

최대 개수는 항상 **추가 전**에만 `>= MAX`로 검사하고, 온보딩의 후행 최대 검사는 각 `likeArtist` 호출이 이미 하므로 제거했습니다.

### 배운 점

1. **검증 함수는 "언제의 상태"를 검사하는지 이름이나 인자로 드러나야 합니다.** 같은 숫자 조건도 작업 전/후에 따라 부등호가 달라집니다.
2. **경계값은 테스트로 고정해야 합니다.** 1, 2, 3개 / 49, 50, 51개 케이스 표를 테스트로 만들었다면 `7b87e55`, `68375a3`의 회귀는 커밋 전에 잡혔습니다. 테스트가 없어 한 달 가까이 수정이 이어졌습니다(아직 테스트 없음 → [operations.md](operations.md#점검-필요-항목)).
3. **트랜잭션 롤백은 조용합니다.** "데이터가 안 바뀌었다"는 증상은 저장 누락보다 롤백을 먼저 의심합니다.

## 3. 좋아요 기능 추가 후 서버가 기동되지 않던 문제 — 시드 초기화와 FK

**담당** 곽동욱 · **커밋** `c8f33e8`(2025-11-12) · 이후 `e4ee02a`(11-20), `4d4fcce`(11-23)

**증상**: 공연 좋아요(`user_performance_like`)를 추가한 뒤 애플리케이션 기동이 실패.

**원인**: 공연 시드 초기화(`PerformanceDataInitializer`, `@PostConstruct`)가 기동할 때마다 `performance_detail`을 `deleteAll()`로 비우고 다시 넣었습니다. 새로 생긴 좋아요 테이블이 `performance_detail.id`를 **FK로 참조**하므로, 좋아요 행이 하나라도 있으면 부모 삭제가 FK 제약에 걸려 초기화가 실패했고 빈 생성 실패로 앱이 뜨지 않았습니다.

**해결**
1. 자식(`user_performance_like`)을 먼저 지우고 부모를 지우도록 순서 조정, `@Transactional`로 묶음.
2. 시드를 `@Profile("dev")`로 격리하고 `spring.profiles.active: dev`를 명시 — 주석으로 `FIXME: 운영단계에서 prod로 변경 후 performanceDataInitializer 무시`를 남김.
3. CI/CD로 실서버 배포가 시작된 뒤(11-20) **배포(=재기동)마다 사용자 좋아요가 지워지는** 문제를 막기 위해 `active: prod`로 전환(`e4ee02a`). 다만 시드에 의존하는 개발 데이터와 충돌해 3일 뒤 `dev`로 되돌렸습니다(`4d4fcce`, "DB충돌해결").

**현재 상태와 남은 위험** `[분석]`
이후 초기화 코드는 `FOREIGN_KEY_CHECKS = 0` + `TRUNCATE` 방식으로 바뀌었고 프로필 조건이 없습니다(손재희, `a0d6ed6`, `3b3d697`). FK 검사를 끄면 기동은 되지만, `TRUNCATE`가 AUTO_INCREMENT를 1로 되돌려 **공연 PK가 다시 매겨집니다.** 사용자 좋아요·타임테이블 커스텀은 공연 PK(`performance_id`)를 들고 있으므로, 시드 목록의 순서나 개수가 바뀐 버전이 배포되면 **좋아요가 엉뚱한 공연을 가리킬 수 있습니다.** → [operations.md](operations.md#공연-시드-데이터와-재배포)

**배운 점**: 새 테이블이 기존 엔티티를 참조하면 **기존의 삭제·초기화 경로가 영향을 받는지**를 함께 점검해야 합니다. 그리고 "개발 편의용 초기화"와 "운영 데이터"는 코드가 아니라 **실행 환경(프로필·별도 스크립트)** 으로 분리해야 합니다.

## 4. 배포 서버에서 Swagger 접근 불가 — 원인을 잘못 짚었던 기록

**담당** 곽동욱 · **커밋** `9029a8b`, `aeab88f`, `456b27a`, `53f5631`, `870cf84`(2025-11-19) → `0cf8f54`, `35f69f0`(11-20)

**증상**: 로컬에서는 열리던 Swagger UI가 배포 서버에서 열리지 않음. 프론트와의 유일한 API 계약서라 급했습니다.

**당시 대응** `[기록]`

| 커밋 | 시도 |
| --- | --- |
| `9029a8b`, `aeab88f` | JWT 필터 제외 목록에 Swagger 경로를 하나씩 추가 |
| `456b27a` | 앞에 다른 경로가 붙었을 가능성을 의심해 `/**/swagger-ui/**` 형태로 변경 |
| `53f5631` | 들어오는 URI를 `System.out`으로 출력, `path.contains("swagger")`면 무조건 통과 |
| `870cf84` | "서버 문제로 인한" `WebSecurityCustomizer.ignoring()`으로 Security 자체를 우회 |
| `0cf8f54` | 다음 날 "서버 정상화로 인한 코드 복구" — `contains` 우회와 디버그 출력 제거 |
| `35f69f0` | OpenAPI 서버 목록에 운영 HTTPS 주소와 로컬 주소를 명시 |

같은 날 손재희가 `server.forward-headers-strategy: native`를 추가했습니다(`9cc359a`).

**회고** `[분석]`
- `JwtAuthenticationFilter`는 토큰이 없거나 틀려도 **요청을 거부하지 않고** 그냥 다음 필터로 넘깁니다. 거부는 인가 단계(`authorizeHttpRequests`)나 진입점이 합니다. 그리고 Swagger 경로는 처음부터 `AUTH_WHITELIST`로 `permitAll`이었습니다. 즉 **필터 제외 목록을 바꾸는 것으로는 이 증상이 생기지도, 고쳐지지도 않는 구조**였습니다.
- 커밋 메시지가 말하듯 원인은 서버 쪽에 있었던 것으로 보입니다. HTTPS 프록시 뒤에서 Swagger가 `http://` 서버 주소로 API 문서를 요청하면 브라우저가 혼합 콘텐츠로 차단하는데, 다음 날 들어간 **서버 주소 명시와 forwarded 헤더 설정**이 바로 이 문제에 대한 처방입니다.
- 확인했어야 할 순서: ① 브라우저 개발자 도구에서 실패한 요청의 **URL·상태 코드** → ② 401/403이면 응답 본문으로 어느 컴포넌트가 막았는지 → ③ 요청 자체가 안 나갔다면 혼합 콘텐츠·CORS.

**배운 점**: 증상이 "접근 불가"라고 해서 가장 최근에 만든 컴포넌트(JWT 필터)를 바로 의심하지 말고, **실패한 요청의 상태 코드와 응답 주체를 먼저 확인**해야 합니다. 그리고 `contains` 우회 같은 응급 처치는 원인이 밝혀지면 반드시 되돌립니다(`0cf8f54`).

## 5. JWT subject를 이메일에서 userId로

**담당** 곽동욱 · **커밋** `de50ec7`, `9e14d8e` · 2025-11-20 · [auth.md](auth.md#왜-sub가-이메일이-아니라-userid인가)

- **문제**: `sub`에 이메일을 넣었는데, 사용자 식별은 `(email, provider)`입니다. 같은 이메일로 Google·Kakao에 각각 가입한 사용자가 있으면 토큰만으로 누구인지 정할 수 없고, 로그인 때마다 이메일이 갱신될 수 있으며, payload에 개인정보가 노출됩니다.
- **해결**: `generateAccessToken(Long userId)`, 필터는 `findById(Long.valueOf(sub))`로 `User`를 읽어 `CustomUserDetails`를 principal로 저장. 1번(IDOR) 해결의 기반이 되었습니다.
- **남은 점** `[분석]`: 형식이 바뀌는 배포 직후, 이전에 발급된(최대 6시간 유효) 이메일 `sub` 토큰이 들어오면 `Long.valueOf`에서 `NumberFormatException`이 납니다. 필터 단계 예외라 전역 핸들러가 잡지 못해 500이 됩니다. 토큰 형식을 바꿀 때는 파싱 실패를 "인증 실패(401)"로 수렴시키는 처리가 필요합니다.

## 6. 모든 예외가 400으로 응답되던 문제 — 에러 계약 정립

**담당** 곽동욱 · **커밋** `5c7a1f7`(11-12) → `33e1046`, `e830c7f`, `35f34f6`, `143b951`, `8936054`, `426a82a`(11-23)

- **증상**: 없는 아티스트(404여야 함), 중복 좋아요(409여야 함), 서버 버그(500이어야 함)가 모두 **400**. 메시지에는 `"유저 없음"` 같은 임시 문자열이나 NPE 등 **내부 예외 메시지가 그대로** 노출.
- **원인**: 초기 전역 핸들러가 `@ExceptionHandler(RuntimeException.class)` 하나로 모든 런타임 예외를 400 + `ex.getMessage()`로 응답했고, 서비스는 `throw new RuntimeException("...")`을 직접 던졌습니다.
- **해결**
  - `ErrorCode` enum(상태 + 메시지)과 `CustomException(ErrorCode)` 도입, 서비스의 `RuntimeException`을 모두 교체.
  - 핸들러를 예외 종류별로 분리: 비즈니스(`CustomException`), Bean Validation(필드별 `validation` 맵), 필수 파라미터 누락, 타입 불일치, 그 외(500 + 고정 메시지 + `log.error` 스택트레이스).
  - `ErrorResDto`에 `@JsonInclude(NON_NULL)` — 검증 오류일 때만 `validation` 필드가 나갑니다.
- **효과**: 프론트가 상태 코드로 분기할 수 있게 되었고, 예상하지 못한 예외는 사용자에게 내부 정보 대신 고정 메시지가, 서버 로그에는 원인이 남습니다.
- **남은 점**: 응답에 `ErrorCode` 이름 같은 **고유 코드 필드가 없어** 같은 400끼리는 메시지 문자열로 구분해야 합니다([ADR 8](design-decisions.md#8-에러-계약--errorcode-enum-한-곳에서-상태와-메시지를-정한다)).

## 7. 최근 검색어 중복·무한 누적

**담당** 곽동욱 · **커밋** `885d791`, `fe7f443` · 2025-11-27 · [search.md](search.md#정책-변경-이력-885d791-2025-11-27)

- **증상**: "검정치마 → 혁오 → 검정치마" 순으로 검색하면 목록에 검정치마가 두 번. 검색할 때마다 행이 무한히 쌓이고 조회만 5개로 잘라 보여줌.
- **원인**: 중복 방지가 "**직전** 검색어와 같은가"만 비교했고, 저장 개수 제한이 없었습니다.
- **해결**: 같은 키워드 기록이 있으면 지우고 새로 저장(맨 위로 이동), 저장 후 5개를 넘으면 가장 오래된 기록 삭제. 사용자당 테이블 크기가 5행으로 묶입니다.

## 8. 로그인 리다이렉트 주소를 바꾸는 커밋이 반복된 문제

**담당** 곽동욱 · **커밋** `1ae4d10`(11-24), `5ea4e72`(12-07), `1e89a5f`, `287aecd`(12-08), `1f28331`(12-09)

- **증상**: 프론트 로컬 개발(`localhost:5173/callback`)과 운영(`stage-on-web.vercel.app/callback`)을 오갈 때마다 `OAuth2SuccessHandler`의 상수를 고쳐 커밋·배포.
- **원인**: 환경마다 다른 값이 **코드 상수**였습니다. 서버는 하나인데 로컬 프론트와 운영 프론트 둘 다 그 서버로 로그인해야 했습니다.
- **개선안**(미적용): `app.oauth2.redirect-uri`를 설정값으로 빼고, 허용 목록 안에서 로그인 요청 시 전달한 `redirect_uri`를 쿠키에 담아 성공 핸들러가 그 주소로 보내는 방식. 임의 주소로 토큰을 보내는 **오픈 리다이렉트를 막기 위해 허용 목록 검증은 필수**입니다.
- **배운 점**: 같은 파일을 같은 이유로 세 번 이상 고치고 있다면 그 값은 코드가 아니라 설정입니다.

## 이 사례들에서 정리한 원칙

1. **요청자의 신원은 서명된 토큰에서만 꺼낸다.** 클라이언트가 보낸 식별값은 입력값이다. (1, 5)
2. **검증 함수는 "언제의 상태"를 검사하는지 드러낸다.** 경계값은 테스트로 고정한다. (2)
3. **"안 바뀌었다"는 저장 누락보다 롤백을 먼저 의심한다.** 응답 상태 코드부터 본다. (2, 4)
4. **새 FK는 기존 삭제·초기화 경로를 깨뜨릴 수 있다.** 개발 데이터와 운영 데이터는 실행 환경으로 분리한다. (3)
5. **응급 처치는 원인이 밝혀지면 되돌린다.** (4)
6. **상태 코드에 의미를 담고, 내부 정보는 로그로만.** (6)
7. **반복해서 바꾸는 값은 설정으로 뺀다.** (8)
